### 1. **Procedural vs. Object-Oriented Design**
- Procedural code makes it easier to add new functions without changing existing data structures. However, adding new data structures requires modifying all related functions.
- In contrast, OOP allows adding new classes with minimal changes to existing functions but requires updates to all classes if new functions are added.

### 2. **Hiding Implementation**
- OOP emphasizes abstraction. Instead of exposing raw data via getters and setters, abstract interfaces should encapsulate the essence of data, allowing manipulation without revealing its internal structure.

### 3. **Polymorphism and Extensibility**
- Polymorphism enables dynamic behavior, where a single interface supports multiple implementations. This avoids creating a monolithic class, like the procedural `Geometry` example, and supports the Open-Closed Principle (OCP)—a class should be open for extension but closed for modification.

### 4. **Law of Demeter**
- A module should only interact with immediate friends (e.g., its own methods or objects directly associated with it) and avoid accessing deeply nested objects through chains of calls (a "train wreck"). This ensures better modularity and encapsulation.

### 5. **Data/Object Anti-Symmetry**
- Objects encapsulate data and expose behaviors, while data structures expose their internal state but lack meaningful functions. This anti-symmetry has significant implications for design, emphasizing that each approach suits different needs.

### 6. **Separation of Concerns and AOP**
- OOP inherently supports modularity but struggles with cross-cutting concerns (e.g., logging or persistence). Techniques like Aspect-Oriented Programming (AOP) address these concerns by non-invasively injecting behavior, maintaining clean class responsibilities.

1. Procedural vs. Object-Oriented Design

    Procedural code makes it easier to add new functions without changing existing data structures. However, adding new data structures requires modifying all related functions.
    In contrast, OOP allows adding new classes with minimal changes to existing functions but requires updates to all classes if new functions are added​

    OOP emphasizes abstraction. Instead of exposing raw data via getters and setters, abstract interfaces should encapsulate the essence of data, allowing manipulation without revealing its internal structure​

​

    .

3. Polymorphism and Extensibility

    Polymorphism enables dynamic behavior, where a single interface supports multiple implementations. This avoids creating a monolithic class, like the procedural Geometry example, and supports the Open-Closed Principle (OCP)—a class should be open for extension but closed for modification​

​

    .

4. Law of Demeter

    A module should only interact with immediate friends (e.g., its own methods or objects directly associated with it) and avoid accessing deeply nested objects through chains of calls (a "train wreck"). This ensures better modularity and encapsulation​

    .

5. Data/Object Anti-Symmetry

    Objects encapsulate data and expose behaviors, while data structures expose their internal state but lack meaningful functions. This anti-symmetry has significant implications for design, emphasizing that each approach suits different needs​

    .
